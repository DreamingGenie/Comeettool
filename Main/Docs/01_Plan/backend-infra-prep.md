# 백엔드·인프라 파트 개발 착수 준비

담당 범위(2인 공동): **AUTH-01~07 / SPACE-01~18 / MEMBER-01~06 / MEET-01~07 / 인프라 전반**
근거 문서: [기능 명세서](functional-specification.md), [서비스 아키텍처](architecture.md)

진행 순서: **① 스택·라이브러리·API 확정 → ② 컨설턴트 상담 → ③ ERD 설계 → ④ 개발**

> 각 표는 **선택 결과만** 기재한다. 표 아래 `후보 분석` 섹션은 선택을 돕기 위한 참고 자료이며, **확정 후 해당 섹션을 삭제**하면 표만 남는다.

## 1. 스택 · 라이브러리 · API 결정

### 1-0. 기반

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| Java 버전 | Java 17+ (유력) | 미디어팀 Kurento **미채택** → **LiveKit 유력**(미확정). LiveKit은 토큰 발급·서버 API 호출로 연동돼 Java 버전 제약이 거의 없음. LiveKit 확정 시 고정 |
| Spring Boot 버전 | 3.x (유력) | Java 17+ 전제. LiveKit 확정 후 고정 |
| 빌드 도구 | Gradle | |

<details>
<summary>후보 분석 (결정 후 삭제)</summary>

**Java / Spring Boot 버전 — 갱신**
당초 Kurento 클라이언트 라이브러리가 지원하는 Java 버전이 Spring Boot 버전을 좌우했으나, 미디어팀이 **Kurento를 채택하지 않기로** 결정했고 **LiveKit이 유력**하다(아직 미확정). LiveKit은 별도 미디어 서버(Go 기반)로 동작하고 백엔드는 **액세스 토큰(JWT) 발급 + LiveKit 서버 API 호출**로 연동되므로, Kurento처럼 Java 버전을 강하게 구속하지 않는다. 따라서 **Spring Boot 3.x / Java 17+** 를 자유롭게 선택할 수 있다. 다만 LiveKit이 최종 확정되기 전이므로 버전 고정은 확정 시점에 마무리한다.

**빌드 도구**

| 후보 | 장점 | 단점 |
|---|---|---|
| Gradle | 빌드 속도 빠름(증분·캐시), 설정 간결(Groovy/Kotlin DSL), 최근 Spring 생태계 주류 | Groovy/Kotlin DSL 문법 학습 필요, 에러 메시지가 불친절할 때 있음 |
| Maven | XML 구조라 명시적이고 예측 가능, 레퍼런스·자료 압도적, IDE 지원 안정적 | 빌드 느림, pom.xml이 장황함 |

**고려 기준**
- 팀원 다수가 익숙한 쪽 (6주 프로젝트에서 빌드 도구 학습에 시간 쓰면 손해)
- 멀티 모듈 구성 계획 여부 (Gradle이 유리)
- CI 빌드 시간 (Gradle 캐시가 GitLab Runner에서 유리)

</details>

### 1-1. 인증 (AUTH)

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| 인증 프레임워크 | Spring Security | |
| JWT 라이브러리 | 미정 | |
| 비밀번호 해싱 | BCrypt | Spring Security 내장, NFR "비밀번호 해시" 충족 |
| Refresh Token 저장소 | Redis | AUTH-04 토큰 폐기(무효화) |
| 토큰 전달 방식 | 미정 | **FE·실시간 담당과 합의 필요** |
| 이메일 발송 | 미정 | AUTH-07(2차), MEMBER-02 초대에 필요 |

<details>
<summary>후보 분석 (결정 후 삭제)</summary>

**JWT 라이브러리**

| 후보 | 장점 | 단점 |
|---|---|---|
| jjwt (io.jsonwebtoken) | 국내 레퍼런스 가장 많음, API 직관적, SSAFY 프로젝트 다수 사용 | 0.11→0.12에서 API 변경되어 옛 예제 그대로 안 됨 |
| java-jwt (Auth0) | 사용법 단순, 문서 깔끔 | JWE 미지원, 국내 자료 상대적으로 적음 |
| nimbus-jose-jwt | 기능 가장 풍부(JWE/JWK 등), Spring Security OAuth2가 내부적으로 사용 | API 복잡, 이번 규모엔 과함 |

**고려 기준**
- 막혔을 때 검색으로 해결 가능한가 (6주 프로젝트에서 레퍼런스 양이 곧 속도)
- 우리는 단순 서명(JWS)만 필요한가, 암호화(JWE)까지 필요한가 → 명세상 JWS로 충분
- 버전별 API 차이 주의: 예제 복붙 시 버전 확인 필수

**토큰 전달 방식** ← 이 결정이 FE·WebSocket 3채널에 모두 영향

| 후보 | 장점 | 단점 |
|---|---|---|
| Authorization 헤더 (Bearer) | 구현 단순, CSRF 안전, 모바일/외부 클라이언트 확장 쉬움, WebSocket 연결 시 다루기 쉬움 | **XSS에 취약**(JS로 토큰 접근 가능), FE가 저장 위치(localStorage 등) 직접 관리 |
| HttpOnly 쿠키 | XSS로 토큰 탈취 불가, 브라우저가 자동 전송 | **CSRF 대응 필요**, WebSocket·크로스 도메인 설정 까다로움, SameSite 정책 신경 써야 함 |
| 하이브리드 (Access=헤더, Refresh=HttpOnly 쿠키) | 양쪽 장점 절충 — 탈취 위험 큰 Refresh만 쿠키로 보호 | 구현 복잡도 증가, FE와 규약 협의 필요 |

**고려 기준**
- **WebSocket 인증에 어떻게 실을 것인가** — 시그널링·채팅·문서 3개 채널이 모두 이 결정에 종속됨. 헤더 방식이 다루기 쉬움
- FE가 Vue SPA이고 같은 도메인(Nginx 뒤)에 배치되는가 → 쿠키가 현실적일 수도
- 6주 규모에서 CSRF 대응 공수를 감당할 것인가
- **이 결정은 내 파트가 토큰을 발급하므로 규약을 우리가 먼저 제시해야 함**

**이메일 발송** (AUTH-07 비밀번호 재설정, MEMBER-02 초대)

| 후보 | 장점 | 단점 |
|---|---|---|
| Spring Mail + Gmail SMTP | 설정 간단, 무료, 즉시 시작 가능 | **일일 발송 한도(500건)**, 스팸 처리될 확률 높음, 앱 비밀번호 관리 |
| AWS SES | 이미 AWS를 쓰므로 통합 자연스러움, 발송량·도달률 우수, 저렴 | **샌드박스 해제 신청 필요**(승인에 시간 소요), 도메인 인증 필요 |

**고려 기준**
- AUTH-07이 2차 우선순위이므로 **당장 필요한 건 MEMBER-02(초대)뿐** — 초대를 이메일 대신 링크/코드 공유로 처리하면 이메일 인프라를 미룰 수 있음
- SES 샌드박스 해제에 시간이 걸리므로, 쓸 거면 **미리 신청**해둬야 함
- 발표/시연 시 실제 이메일 발송이 필요한가

</details>

### 1-2. 팀스페이스 · 회의 도메인 (SPACE / MEMBER / MEET)

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| ORM | Spring Data JPA (Hibernate) | |
| DB 마이그레이션 | 미정 | 7인 병렬 개발 — 스키마 충돌 방지 |
| 동적 쿼리 | 미정 | SPACE-04 검색/필터 |
| 권한 검사 방식 | 미정 | NFR "스페이스·회의·문서 단위 접근 검사" |
| 초대 링크/코드 | UUID 토큰 + 만료 | SPACE-12, MEMBER-02 |
| API 문서화 | 미정 | FE 협업용 |

<details>
<summary>후보 분석 (결정 후 삭제)</summary>

**DB 마이그레이션** ← 7인이 각자 엔티티를 만들면 스키마가 반드시 충돌한다. 도입 권장.

| 후보 | 장점 | 단점 |
|---|---|---|
| Flyway | SQL 그대로 작성해 직관적, 설정 단순, 학습 30분이면 충분 | 롤백이 유료(Teams), DB 종속적 SQL |
| Liquibase | XML/YAML/SQL 지원, DB 독립적, 롤백 무료 지원 | 설정 복잡, 추상화 레이어 학습 필요 |
| 미사용 (JPA `ddl-auto`) | 초기 개발 속도 빠름 | **운영에 절대 부적합**, 팀원 간 스키마 불일치, 데이터 날아감 |

**고려 기준**
- **PostgreSQL 마이그레이션 계획이 있다면 Liquibase의 DB 독립성이 유리**할 수 있음 (다만 그건 AI DB가 아니라 백엔드 DB의 향후 전환 얘기)
- 팀에 SQL이 편한 사람이 많으면 Flyway
- 최소한 `ddl-auto: validate` + 마이그레이션 도구 조합은 갖출 것. `update`로 6주를 버티면 통합 때 문제가 터짐

**동적 쿼리** (SPACE-04 검색·필터, 확장 우선순위)

| 후보 | 장점 | 단점 |
|---|---|---|
| Spring Data JPA 기본 (메서드 쿼리 + `@Query`) | 추가 의존성 없음, 간단한 조회엔 충분 | 조건 조합이 늘면 메서드 폭발, 동적 조건 처리 불가능에 가까움 |
| QueryDSL | 타입 안전(컴파일 시점 오류 검출), 동적 조건 조합 깔끔, JPA와 궁합 좋음 | Q클래스 생성 설정 필요(Gradle/Maven 설정이 은근 까다로움), 학습 곡선 |
| MyBatis | SQL 완전 제어, 복잡한 쿼리 자유 | JPA와 혼용 시 관리 포인트 이원화 |

**고려 기준**
- SPACE-04가 `확장` 우선순위 → **MVP엔 동적 쿼리가 거의 불필요**. 나중에 필요할 때 QueryDSL을 추가해도 늦지 않음
- 다만 QueryDSL은 빌드 설정을 나중에 끼워넣기 번거로우니, 쓸 거면 **초기 세팅 때 넣는 게 편함**
- 회의 목록(MEET-02) 필터(예정/진행/종료)가 얼마나 복잡해질지 고려

**권한 검사 방식** ← NFR에 "스페이스·회의·문서 단위 접근 검사"가 명시됨. 3단 검사가 필요.

| 후보 | 장점 | 단점 |
|---|---|---|
| `@PreAuthorize` + 커스텀 `PermissionEvaluator` | Spring Security 표준, 선언적이라 코드 깔끔, 메서드 단위 적용 | SpEL 문법 학습, 디버깅 어려움, DB 조회가 끼면 성능 주의 |
| 커스텀 AOP / 인터셉터 | 동작이 명시적이라 이해·디버깅 쉬움, 자유도 높음 | 직접 구현·유지보수 부담, 적용 누락 위험 |
| 서비스 레이어에서 직접 검사 | 가장 단순, 명확 | **검사 누락이 발생하기 쉬움**(보안 사고), 중복 코드 |

**고려 기준**
- **누가 이 공통 모듈을 소유할 것인가** — 문서(DOC-07)·회의(MEET) 담당자도 써야 하므로 우리가 만들어 제공해야 함
- Owner/Member/Guest 3역할 × 스페이스/회의/문서 3계층 조합을 어떻게 표현할지
- 검사 누락을 막는 장치가 있는가 (선언적 방식이 유리)

**API 문서화**

| 후보 | 장점 | 단점 |
|---|---|---|
| springdoc-openapi (Swagger UI) | 코드에서 자동 생성, FE가 바로 테스트 가능, 설정 간단 | 어노테이션이 코드에 섞임, 문서 품질이 어노테이션 성실도에 좌우 |
| Spring REST Docs | 테스트 기반이라 문서와 실제 동작 불일치 없음, 문서 품질 높음 | 테스트를 반드시 작성해야 함, 초기 설정 부담, 6주엔 부담 |
| 수기 문서 (노션 등) | 자유로움 | 코드와 반드시 어긋남, 유지보수 안 됨 |

**고려 기준**
- FE 1명 + 풀스택 5명이 API를 써야 함 → **FE가 직접 호출 테스트 가능한가**가 중요
- 6주 규모에서 REST Docs의 테스트 작성 비용을 감당할 수 있는가

</details>

### 1-3. 인프라

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| 리버스 프록시 | Nginx | TLS 종료, 경로 라우팅 (`/api`, `/ws`, `/ai`, 정적) |
| TLS 인증서 | 미정 | |
| 컨테이너 | Docker + Docker Compose | |
| CI/CD | GitLab Runner | 파이프라인 범위 미정 |
| 배포 구성 | 미정 | 인스턴스 수·SFU 분리 여부 |
| 시크릿 관리 | 미정 | |
| S3 업로드 방식 | 미정 | |
| 모니터링 | Prometheus + Grafana + Loki | Spring Actuator + Micrometer, Promtail |

<details>
<summary>후보 분석 (결정 후 삭제)</summary>

**배포 구성** ← 컨설턴트 질문 대상

| 후보 | 장점 | 단점 |
|---|---|---|
| 단일 EC2에 전부 (Docker Compose) | 구성 단순, 비용 최소, 관리 쉬움 | **SFU가 CPU/대역폭을 독점하면 API 서버까지 죽음**, 확장 불가 |
| SFU 분리 (API/SFU 2대 이상) | 미디어 부하 격리, 장애 전파 차단 | 비용↑, 네트워크·배포 구성 복잡 |
| + AI 서버 분리 | STT·LLM 처리가 무거워 격리 필요 | 비용↑ |

**고려 기준**
- **최대 10명 × 동시 3개 회의실**의 실제 부하가 얼마인가 → 컨설턴트에게 EC2 타입 권고를 물어볼 것
- SFU는 UDP 포트 대역을 열어야 해서 보안 그룹 설정이 API와 다름
- SSAFY 제공 서버 스펙·대수 제약 확인 필요
- **TURN(coturn) 서버**가 필요한지도 함께 결정 (방화벽 뒤 참여자 연결)

**시크릿 관리**

| 후보 | 장점 | 단점 |
|---|---|---|
| .env 파일 (gitignore) | 가장 단순, 즉시 시작 | 팀원 간 공유가 수동(카톡·노션으로 흐름 = 유출 위험), 서버마다 수동 배치 |
| GitLab CI/CD Variables | CI에서 자동 주입, GitLab에 이미 있음, 마스킹 지원 | 로컬 개발엔 별도 방법 필요 |
| AWS Parameter Store / Secrets Manager | 중앙 관리, 감사 로그, 권한 제어 | 설정 공수, AWS SDK 연동 필요, Secrets Manager는 유료 |

**고려 기준**
- NFR에 "보안 — 저장 데이터 암호화"가 있음. 최소한 **DB 비밀번호·JWT 시크릿·AWS 키가 Git에 올라가지 않는 것**이 마지노선
- 로컬(dev)과 배포(prod)를 어떻게 다르게 줄 것인가
- 현실적으로 **로컬은 .env + 배포는 GitLab CI Variables** 조합이 6주 규모에 무난

**S3 업로드 방식** (AUTH-05 프로필 이미지, CHAT-04 첨부)

| 후보 | 장점 | 단점 |
|---|---|---|
| 서버 경유 (파일 → Spring → S3) | 서버가 검증·리사이징 가능, 구현 단순, 권한 제어 명확 | **서버 대역폭·메모리 소모**, 대용량(녹화·오디오)엔 부적합 |
| Presigned URL (FE → S3 직접) | 서버 부하 없음, 대용량에 유리 | FE 구현 복잡, 업로드 완료 확인 로직 필요, 검증이 어려움 |

**고려 기준**
- 프로필 이미지는 작지만 **회의 녹화(RTC-08)·오디오 원본(AI-01)은 큼** → 용도별로 다르게 가도 됨
- **FE와 합의 필요** (presigned면 FE 작업이 생김)
- 오디오·녹화는 미디어팀/서버가 직접 올리므로 우리 파트 범위인지 경계 확인

**TLS 인증서**

| 후보 | 장점 | 단점 |
|---|---|---|
| Let's Encrypt + certbot | 무료, 자동 갱신 | 도메인 필요, 갱신 설정 |
| SSAFY 제공 도메인·인증서 | 별도 작업 불필요 | 제공 범위 확인 필요 |

**고려 기준**
- **WebRTC는 HTTPS/WSS가 사실상 필수** → 인증서 없이는 미디어팀이 개발·테스트를 못 함. **우선순위 높음**
- 도메인 발급 여부를 SSAFY 측에 먼저 확인

**CI/CD 파이프라인 범위**

| 후보 | 장점 | 단점 |
|---|---|---|
| build → test → deploy 전체 자동화 | 배포 부담 없음, 통합 빠름 | 초기 구축 시간, 배포 실패 시 디버깅 |
| build → test만 (배포는 수동) | 구축 빠름 | 배포 때마다 수동 작업 |

**고려 기준**
- 7인이 병렬 개발 → **최소한 `main` 병합 시 빌드·테스트 자동 실행**은 있어야 깨진 코드 병합을 막음
- 배포 자동화는 develop→dev서버, main→prod서버 식으로 나눌지
- 초반 1~2주 안에 구축해야 이후가 편함 (나중에 하면 계속 미뤄짐)

## 2. 합의해야 할 내용

### 2-1. 팀 전체 합의 사항

| # | 안건 | 대상 | 왜 중요한가 |
| --- | --- | --- | --- |
| 1 | Java / Spring Boot 버전 | 미디어팀 | Kurento 미채택·LiveKit 유력으로 미디어 라이브러리 종속성 해소. LiveKit 확정 시 Java 17+/Spring Boot 3.x 고정 |
| 2 | API 공통 규약 — REST 네이밍, 응답 포맷(래퍼 여부), 에러 코드 체계, 페이징 | 전체 | 나중에 통일하려면 전부 고쳐야 함 |

| 4 | 권한 검사 공통 모듈 — 우리가 만들어 제공할지, 각자 구현할지 | 전체 | DOC-07·MEET 담당도 사용. 중복/누락 방지 |

| 6 | **AI 연동 인터페이스** — SQS 메시지 스키마, 완료 통보(웹훅/폴링), AI-10 상태 저장 위치 | AI 담당 | 우리가 트리거·상태를 관리. **ERD 설계 전 필수** |
| 7 | **회의 종료 → 오디오 취합 책임 경계** — 누가 S3에 올리고 누가 SQS에 넣는가 | 미디어팀, AI | 3자 경계. 비면 아무도 안 함 |
| 8 | 패키지 구조(도메인형/계층형), 코드 컨벤션, 로깅 포맷(Loki 라벨 규칙) | 전체 | |
| 9 | 배포 구성 — 인스턴스 분리, 포트·보안그룹 | 미디어팀 | SFU UDP 포트 요구사항 확인 |

### 2-2. 함께 담당하는 1인과 합의

1. **2인 내부 분담** — 예시: A = 인증(AUTH) + 인프라/CI-CD, B = 스페이스·멤버(SPACE/MEMBER) + 회의 도메인(MEET)
2. **공통 코드 소유권** — 인증 필터, 권한 검사, 예외 처리, 응답 래퍼를 누가 만들고 언제까지 제공하는가 (다른 팀원이 기다림)
3. **ERD 초안 작성 주체와 리뷰 방식**
4. **로컬 개발 환경 통일** — Docker Compose(MySQL·Redis) 구성 파일 공유
5. **작업 순서** — 인프라·공통 모듈이 먼저 나와야 나머지가 굴러가므로, 초반 우선순위 조율

## 3. 컨설턴트 상담 질문지

### A. 프로젝트 최대 리스크
1. **미디어 서버로 LiveKit이 타당한가?** (Kurento는 유지보수 정체·셋업 난도로 **미채택**) mediasoup / Janus 대비 LiveKit 권고 여부. **참여자별 오디오 트랙 분리가 실제로 가능한가** — 이것이 AI 회의록 전체의 전제(§7)라, 불가능하면 아키텍처가 뒤집힘
2. **6주 / 7인에 이 범위가 현실적인가?** MVP를 줄인다면 어디부터 잘라야 하는가
3. **AI 1인 배치가 병목 아닌가?** 핵심 차별점인데 인력 재배치가 필요한가

### B. 백엔드·인프라 파트
4. **JWT + Redis 토큰 무효화 구조**가 이 규모에 적절한가 (과한지/부족한지)
5. **WebSocket 인증 베스트 프랙티스** — 시그널링·채팅·문서 3개 채널에 토큰을 어떻게 실어야 하는가. Access 토큰 만료 시 연결 처리는?
6. **권한 검사를 Nginx(게이트웨이)가 아닌 Spring 필터에 두는 판단**이 맞는가. 스페이스·회의·문서 3단 검사 구현 권고
7. **DB 2개(백엔드 MySQL + AI PostgreSQL) 분리가 과한가?** 6주 규모에서 운영 부담 대비 이점이 있는지, 단일 DB 권고인지. 분리 시 두 DB 간 ID 정합성 관리 권고
8. **인프라 구성** — SFU를 별도 인스턴스로 분리해야 하는가? EC2 타입·대수 권고. **TURN(coturn) 서버가 필수인가**
9. **최대 10명 / 동시 3개 회의실**이 권고 인스턴스에서 감당 가능한 수치인가. NFR 수치(입장 5초 이내, 문서 동기화 500ms) 현실성
10. **CI/CD 구축 범위** — 6주 프로젝트에서 어디까지 자동화하는 게 투자 대비 효율적인가

### C. 정책 · 비용
11. **STT 비용** — 실제 예산 규모는? Google Cloud STT / pyannoteAI / Whisper 중 한국어 회의 기준 권고. **GMS-key 이중 사용 구조**가 타당한가
12. **음성 원본 5년 보관**이 적절한가. 개인정보 동의 방식 권고 (녹음 전 동의, 삭제 정책)
13. **AI 회의록 / 피드백 보고서 품질 검증** — 템플릿 지참, 보고서 내용 품질에 대한 검증 (기존 계획된 질문)
